Never stricter than the harness: a decision that needs a person is now left to the harness's native permission flow (no `PreToolUse` or `PermissionRequest` decision, and no Codex output), so the user's own allow rules and the native "don't ask again" prompt apply again. Only the profile's new `alwaysAsk` hard list still asks (Claude Code and Copilot `ask`, Codex deny with the `approve` command). Rule ids, on by default: `force-push`, `delete-unmerged-branch`, `remove-worktree-force`, `git-clean`, `harness-settings`, `policy-profile`, `human-patterns`; off by default: `credential-read`, `cloud-write`, `destructive-other`. Entries may also be decision categories. The rules match what the shell would run (quotes removed, `eval`/`sh -c` and substitutions read, `cd` followed) and fail closed on opaque Git invocations, under every profile. Git aliases are resolved with `git config --get alias.<name>` and judged by their expansion; the permissive profile no longer approves a Git subcommand that is neither built in nor an alias. A hard-list request is never classified, and no classification approves it. The "Needs classification" block is opt-in with `classify: true` (default `false`). Deferrals are audited as decision `native` with the reason in `deferred`, and `replay` reports how many escalations defer, block for classification or still ask.

**Migration.** With this version, credential and secret reads, protected-path writes, cloud writes and destructive commands outside the hard list are decided by the harness's own permission rules, not by the policy. A broad allow rule (for example `Bash(az:*)` in Claude Code) or Codex with `approval_policy = "never"` or a full-access sandbox runs them without a prompt. To keep asking for them, add the ids to the profile's `alwaysAsk` together with the defaults: `credential-read` (secrets and credential paths), `cloud-write` (cloud changes and deletions), `destructive-other` (`rm -rf` outside a worktree, `git reset --hard`, `git checkout -- .`, `git stash drop`, publishing), or the categories `sensitive`, `destructive` and `unknown` for the broadest form. `classify: true` restores the classification block for ambiguous requests.
