# @agent-corpus/policy-manager

## 0.12.1

### Patch Changes

- Inline interpreter code that edits files through a variable no longer asks a person as a possible policy-state change when every name it uses is plain: bindings are read outside string literals (source text being written is data), keyword arguments (`open(p, encoding=...)`) are not tuple assignments, and a name bound to literals keeps those values. Names resolve only in code that uses a short list of plain names, members and modules; code that reaches anything else (a built-in or global rebound by a decoy, `gc`, `pkgutil`, frame globals, `require("vm")`, a bracket access by string or by a computed index) resolves nothing, so its non-literal paths fail closed as before. A path built from a concatenation or a function parameter is not followed and asks, as on 0.12.0.

## 0.12.0

### Minor Changes

- Fewer false asks, from a replay of real transcripts, where the result is certain; anything uncertain keeps the 0.11.2 decision. `self-approve`: naming `approve` with the CLI still counts everywhere except inside a `git commit -m/-F` message, a `gh pr create/edit/comment --body/-b` or `gh api -f body=` body, and an `npm view`/`info`/`ls`/`install`/`outdated` of the package; `command -v pm` and `v=$(npm view ...)` no longer run the CLI, and interpreter code runs it when it imports the package or can start a process and names the CLI. `policy-state`: inline code that only calls file functions on literal non-state paths is data however much `acp` text it holds (a variable needs exactly one binding; `process.argv`/`sys.argv` words count only when nothing changes argv and node cannot read them as options); in a plain script (no pipe, background job, subshell, substitution, assigning expansion, function, `read`/`export`/`eval`/`source`/`pushd`/`cd -`) a variable bound once to a literal, or by a literal `for` list, is filled in; find's name and path patterns and `-newermt`-style predicates are read-only. `gh api graphql` with an allow-listed literal mutation and variable fields from a literal loop is not `repo-delete`, while a `query` field with an expansion now is. A path under `.claude/worktrees/<name>/` is judged inside that worktree.

- Stricter: a file the script writes and then runs (`sh f`, `python3 f`, `./f`) is judged as code (a literal body gets the full rules, anything else is `policy-state`), and so is `npm pkg set scripts.*` before `npm run`; `find` output read by another command (`| xargs cat`, `cat $(find ...)`) is `credential-read` when it can reach the session files; inline code that writes a path with a session directory name counts whatever uid it names.

- Writes of `*.md` files directly in Claude Code's auto-memory directory (`<CLAUDE_CONFIG_DIR or ~/.claude>/projects/<project>/memory/`, `MEMORY.md` included) are approved, by Write, Edit, a redirection or `tee`, as Claude Code itself does not ask. No `..`, no symlink on the way, no hard-linked file, and not after a command that can create a symlink; the rest of `~/.claude` stays protected.

- Credential reads are what reaches the agent, not a CLI using its own stored login. Reads of Git's own files other than `config`, `config.worktree` and credential files (a worktree's `HEAD`, `gitdir`, `commondir`, `locked`, its `.git` file, `GIT_DIR=`/`--git-dir=` naming the directory) are no longer `credential-read`; a recursive read of a Git directory, `.git/config`, token and secret commands, `env`/`printenv` and a secret passed straight into another command still are, and so is printing a variable named like a secret (`echo $GITHUB_TOKEN`).

- Python or Node running inline code that calls no link, rename, move or copy function and starts nothing no longer counts as a command that can create a symlink, so a memory or temp write after it is judged normally.

- Stricter: a file written and then run through a launcher (`uv run`, `npx tsx`, `deno run`, `bun`) is judged as code; a `printf` or `echo` body that the program would expand is not known, so running it counts as reaching the state; `find` output saved to a file is a credential read when it can reach the session files.

- `pm --version`, `pm --help` and `pm help` print the version or the subcommands without a session service.

- Codex `apply_patch` accepts every documented form: absolute, relative and Windows paths and paths with spaces in `Add`/`Update`/`Delete File` and `Move to` headers, `@@` with or without context, `*** End of File`, CRLF line endings, a trailing newline after `*** End Patch`, and the patch under `command`, `patch` or `input` (the first string holding a patch, so an argv array in `command` is skipped). Each target is judged by the worktree, protected and temp rules; a malformed patch still goes to a person.

- Add `credentialUses` to the profile (permissive only, no defaults): a credential a command reads only to hand straight to one consumer, as a literal source command shape and consumer shapes in the `credentialHelpers` token syntax. The command must be exactly `NAME=$(source) consumer ...`, with `NAME` a credential variable (`*_TOKEN`, `*_PAT`, `*_PASSWORD`, `*_SECRET`, `*_API_KEY`, `*_ACCESS_KEY`; never a loader or option variable such as `NODE_OPTIONS`, `LD_PRELOAD` or `BASH_ENV`), or a consumer whose one `$SECRET` argument carries `$(source)`; no other expansion, operator, redirection or here-document. The consumer is then judged on its own. A consumer that loads code or settings from the worktree or home (a config file, a local `node_modules/.bin`, `~/.curlrc`) can leak the secret: name an exact binary path or fixed config in the pair.
- Read commands that print a secret are `credential-read`: `gh auth status --show-token`/`-t`, `gh config get oauth_token`, `kubectl config view --raw`/`--flatten`, `helm get values`/`all`/`manifest`, `aws lambda get-function(-configuration)`, `aws ssm get-parameter --with-decryption`, `aws sts get-session-token`, `aws ecr get-login-password`, `gcloud secrets versions access`, app settings and registry credentials. So are `git remote -v`, `git config --get remote.*.url`, `git config -l` and `git ls-remote --get-url` when a remote URL carries user info or an `http.extraheader` is set (read at decision time), and reading `client_secret*.json`, `*.p8`, `*.jks`, `*.keystore`, `*.ppk`, every `id_<type>` SSH key, `.curlrc`, `.gitconfig`, `.wgetrc`, `.yarnrc` and `~/.config/{curl,git,pip,yarn,npm}` (writing them is protected). Git config through a glob or brace, its backups (`config.lock`, `config~`), and Grep or Glob on a Git directory are credential reads again (#38).
- `node|python|perl|ruby|php|deno|bun <file>` in a checkout runs without review only when the file is tracked and identical to its blob on origin's default branch, no code file in the checkout is modified or untracked (`git status`, so ignored `node_modules` does not count), and nothing earlier in the same command writes or changes files; an edited, untracked or not yet written script goes to the classifier. A credential helper after any command that may change files in the same script goes to a person (#48).
- Interpreter code that calls a function it names indirectly (a computed member, `getattr`, an import alias, a function reference, Ruby `send`/`public_send`, Perl symbolic calls, PHP variable functions) is not engine-approved, and is judged by every path it names for the policy state. `gh project delete`/`close`/`item-delete`/`item-archive`/`field-delete`/`unlink`/`mark-template` and `gh repo autolink create/delete` are on the floor. The hard-rule memo now lasts only for one decision, so no later request sees a stale answer (#53).
- A file tool's request hash ignores a description or tool-use id, and the working directory when every path is absolute (#40).
- `GIT_DIR=`/`GIT_WORK_TREE=` (as a prefix or `export`) are no longer an environment override when they are literal paths that confine git to one verified feature worktree: both set to the same worktree, or one set and every directory the command may run in inside that worktree (with `GIT_DIR` alone git uses the current directory as the work tree). Exports that differ between branches of the script, `unset` or a bare `export` of them still ask. `git remote set-head`, `set-url`, `add`, `rename`, `remove` and `set-branches` are hard `protected`; `git remote show` and `git var -l` are credential reads under the same remote-URL check.
- Inline Python or Node counts as unable to create a symlink only when it loads `re`, `json`, `sys`, `os`, `pathlib`, `textwrap`, `collections`, `fs` or `path` and every call is on a short read/write/string list; archive extraction and any other call still taint.

## 0.11.2

### Patch Changes

- Claude Code: a yes to the hook's ask is remembered when Claude Code showed the person a dialog for it (a `PermissionRequest` for the same request after the ask, then a successful `PostToolUse`), in any permission mode except `bypassPermissions` and `dontAsk`, so `auto` mode no longer asks again for the same protected file. Codex: a request that needs a person now waits in the `PreToolUse` hook (10 minutes by default, `setup-hook-codex --approval-wait <seconds>`) while the user runs `pm approve --last`, which asks "Allow just this once, or for this session? [o/s/N]"; on approval the command runs with no retry, and without one it is denied as before. Re-trust the Codex `PreToolUse` hook in `/hooks` after setup. In a linked feature worktree, `.agent-config/**`, `.agents/**`, `AGENTS.md` and `CLAUDE.md` are ordinary code; harness settings and hooks, `.codex`, `.github`, the policy profile, and everything in the main checkout or on the default branch stay protected.
- Security: an agent cannot approve its own request. Any agent shell command that runs the policy-manager CLI by any name (`pm`, `pm.cmd`, a path ending in `/pm`, `policy-manager`, its `cli.js`, `npx`/`npm exec` of the package), through any wrapper or subshell and however the subcommand is spelled, is the hard item `self-approve`, except a few literal read-only subcommands. `approve` refuses to run below any live session's harness process or any Claude Code, Codex or Copilot process (a backstop). Reading anything in a policy session directory but its audit logs (the token above all), by any tool or shell reader, is a hard `credential-read`. The engine never approves a command whose program name is computed at run time (`$X`, `$p$q`, `${a}m`); it goes to the classifier, and a computed program followed by a CLI subcommand is `self-approve`.
- A worktree whose default branch is unknown (no `origin/HEAD`, no `main` or `master`) is not a feature worktree. `git checkout`/`restore` of a protected file in the main checkout is a hard `protected` item. A waiting Codex hook counts its own start-up, denies at once when the service is unreachable, and audits a wait once at its start and once at its end.
- Inline interpreter code that edits a temp file outside the policy state is no longer hard `policy-state`: `Path(<literal>)`, `open(<literal>)` and `os.path.join` of literals (directly or through a variable assigned once) are literal paths, a string `.replace(a, b)` is not a file call, and data passed to a write is not a target. A request that could change the policy manager's own files now says so, instead of the cloud/repository/publishing reason.

## 0.4.0

### Minor Changes

- The permissive profile now understands whole shell scripts, not just chains of simple commands, and judges every command that could run. New syntax: quoted-delimiter heredocs and here-strings (`git commit -m "$(cat <<'EOF' ... EOF)"`, `cat <<'EOF' > file`), comments, line continuation, `&`, `&>`, `|&`, `<(...)`, `( ... )`, `{ ...; }`, `for`, `while`, `until`, `if`, `case`, and a literal `$` at the end of a regex.
  
  Variables: `NAME=value`, `export NAME=value` and `for NAME in a b c` give a variable a known value, and the command is judged with it substituted, in every directory and for every value it could take (so `X=rm; $X -rf y` is destructive). Variables assigned in only some branches, in a loop, or from a command, and environment variables the script did not assign (which can hold credentials), are unknown; an unknown value is accepted only as an argument to `echo`, `printf` with string conversions, `test`/`[` without numeric operators, `true`, `false`, `basename` and `dirname`, or as the value of a commit or PR message option, and never as a program, option, path, `cd` target or redirection target.
  
  Heredocs and interpreters: a shell fed by a heredoc has its body judged as a script. An interpreter fed by a heredoc, here-string or `-c` is treated like inline code: the code is scanned for file deletion, process creation, string evaluation and protected paths, which now also applies to `-c` and `-e` code that was previously not read. Code piped into an interpreter still needs a human.
  
  Tightened: `ssh` and database clients (`psql`, `mysql`, `sqlite3`, ...), `trap`, `alias`, `declare` and similar builtins, `printenv`, bare `env` and `set`, assigning `IFS`, `PS4`, `CDPATH` and similar through any route (prefix, plain assignment, `export`, `for`, `read`, `unset`, `printf -v`), a glob in a command name or option (`r[m] -rf x`), and `cd` or `export` behind `command` or `time`. Unquoted `$[`, `$=`, `$^`, `$~` and `$((`, which zsh and bash evaluate, are still rejected.

## 0.3.0

### Minor Changes

- The shell parser now understands two kinds of expansion instead of rejecting every `$`. `$HOME` and `${HOME}` are substituted, so `ls $HOME/x` is judged on its real path. Parameters whose value is unknown (`$?`, `$#`, `$$`, `PIPESTATUS`/`pipestatus` entries) are accepted like a command substitution result, so `echo "exit: ${pipestatus[1]}"` is judged on its real command but the unknown value can never become a program, option, path or redirection target. Command substitution (`$(...)` and backticks, including nested and quoted) is judged by evaluating the inner command with the same rules before the outer command; its output (and the unknown parameters above) is accepted only as an argument to `echo`, `printf`, `test`, `[`, `true`, `false`, `basename` and `dirname`, and never as a program, `cd` target, redirection target, wrapper word (such as an `env` assignment or `timeout` duration), or argument to any other command. Other variables, arithmetic expansion, `$'...'` and heredocs are still sent to a human.
  
  Security: the protected-path list now also covers `~/.config/gh`, `~/.config/gcloud`, `~/.config/op`, `~/.docker`, `~/.gnupg`, `~/.git-credentials`, `~/.password-store`, `~/.vault-token`, `~/.pgpass`, `~/.my.cnf` and `~/.pypirc`, which the permissive profile could previously read.

## 0.2.1

### Patch Changes

- Security: a quoted or escaped value in a leading assignment (`FOO="a b" rm -rf x`, `FOO=a\ b git push --force`) made the parser treat the whole `FOO=...` word as the program, so the real command after it was never checked and could be auto-approved. Leading assignments are now recognised from their plain `NAME=` prefix regardless of quotes or escapes in the value. Appended and indexed forms (`FOO+=x`, `FOO[0]=x`) and assignments with a quoted or escaped name, which the parser cannot represent, are rejected so a human reviews them, and `env` treats any `NAME…=value` word as an assignment before judging the program that follows. Present in 0.2.0 and earlier permissive-profile releases; upgrade to 0.2.1.
